36/// @brief The `propose_screen` tool: the assistant proposes an RFC 6902 JSON Patch to the open screen's document,
37/// which the server applies, checks as it checks a save and, once accepted, hands to the client as the
38/// window's draft.
39///
40/// - **Offered** only on a screen whose document is known and within `ChatLimits::maxDraftBytes`: the turn's draft,
41/// else the bundle's own text for an application screen, else the person's custom screen as @p screens answers it.
42/// On any other screen it is not offered, and the system text says the assistant cannot edit the screen.
43/// - **Its context** is the document, written as one JSON string literal inside a block named as the screen being
44/// edited and as data, never as instructions (a shared custom screen is text someone else may have written), when
45/// it is within `ChatLimits::maxInlineDocumentBytes`, and an outline of it (about 8 KiB at most) otherwise; what
46/// the base rule allows a screen based on the same base; and a short reference to the vocabulary.
47/// - **A call** carries `patch`, an array of operations of at most `ChatLimits::maxProposalBytes` as JSON. The
48/// operations apply one at a time to a copy of the turn's current document, which is the latest draft accepted in
49/// this turn and otherwise the document the turn began on; there is no base to name, since the server is the only
50/// writer within a turn. A whole new document is one `replace` of the path `""`. The call is refused as a tool
51/// error when the arguments are malformed, an operation does not apply (the error names its index, counted from 0,
52/// its kind and path, and nothing is applied), the result is not an object with the open screen's `id`, is longer
53/// than `ChatLimits::maxDraftBytes`, or fails the checks of a save under the turn's session (the error keeps the
54/// pointer into the patched document). Only an accepted result becomes the turn's draft. The refusal that is the
55/// `ChatLimits::maxProposalsPerTurn`th of a turn ends the turn, and the screen stays as it was.
56/// - **The conversation** keeps a patch under about 4 KiB as the model wrote it, and of a larger one only its size
57/// and content hash.
58///
59/// The tool saves nothing, and runs as the turn's session.
60/// @param screens The handle `registerCustomScreens` returned: the checks and the store.
61/// @param app The application's id, as @p screens serves it.
62/// @param executor Where the tool's checks run. Borrowed: it outlives every turn.
63/// @return The tool, for `ChatOptions::tools`.
64[[nodiscard]] MORPH_API ChatTool customScreensChatTool(std::shared_ptr<CustomScreens> const& screens,
65 std::string const& app, exec::IExecutor& executor);

67/// @brief The read tools that go with `propose_screen`: `screen_outline`, `screen_find` and `screen_node`.
68///
69/// They read the turn's current document (see `ChatToolContext::document`), so an answer includes what an accepted
70/// proposal earlier in the turn changed. They are offered under the same conditions as `propose_screen`, and an answer
71/// is capped in bytes (12 KiB, or `ChatLimits::maxToolResultBytes` when that is smaller): `screen_outline` shows the
72/// deepest levels that fit, `screen_find` lists at most 50 matches and says how many more there are, and
73/// `screen_node` shows a smaller depth than asked when the asked one does not fit.
74/// @param screens The handle `registerCustomScreens` returned.
75/// @param app The application's id, as @p screens serves it.
76/// @param executor Where the tools' offers run. Borrowed: it outlives every turn.
77/// @return The tools, for `ChatOptions::tools`.
78[[nodiscard]] MORPH_API std::vector<ChatTool> customScreensReadTools(std::shared_ptr<CustomScreens> const& screens,
79 std::string const& app,
80 exec::IExecutor& executor);
