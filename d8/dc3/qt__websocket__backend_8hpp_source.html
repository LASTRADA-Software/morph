24/// @brief Reconnect tuning for `QtWebSocketBackend`.
25///
26/// Declared outside `QtWebSocketBackend` so its default initialisers are fully
27/// parsed before any constructor default argument that names `Config{}` is
28/// evaluated (same rationale as `morph::offline::NetworkMonitorConfig`).
29struct QtWebSocketBackendConfig {
30 /// @brief Whether to attempt automatic reconnect after an unsolicited disconnect.
31 bool reconnectEnabled = true;
32
33 /// @brief Delay before the first reconnect attempt after a disconnect.
34 std::chrono::milliseconds initialReconnectDelay = std::chrono::milliseconds{500};
35
36 /// @brief Upper bound on the exponential backoff between reconnect attempts.
37 std::chrono::milliseconds maxReconnectDelay = std::chrono::seconds{30};
38
39 /// @brief Multiplier applied to the delay after each failed attempt.
40 double backoffMultiplier = 2.0;
41
42 /// @brief Opt in to `registerModelAsync` (see its doc comment on `IBackend`).
43 ///
44 /// Defaults to `false`: `Bridge::registerHandler()` then falls back to the
45 /// synchronous `registerModel`, exactly as before this feature existed —
46 /// every existing embedder (a desktop Qt client, this backend's own test
47 /// suite) keeps registering synchronously, immediately usable the line
48 /// after `BridgeHandler`'s constructor returns.
49 ///
50 /// Set `true` only for a build where that synchronous guarantee cannot
51 /// hold at all — a WASM main thread, where the nested `QEventLoop`
52 /// `registerModel` relies on aborts the page outright. Doing so is a
53 /// deliberate trade: the caller must then wait for registration to
54 /// complete (e.g. gate the UI on it) before firing an action through that
55 /// handler, since `executeVia` fails fast with "handler not bound" for an
56 /// unbound binding rather than queuing or blocking.
57 bool asyncRegistrationEnabled = false;
58};

60/// @brief `IBackend` implementation that communicates with a `RemoteServer` over WebSocket.
61///
62/// `registerModel()` is synchronous (blocks the calling thread via a nested
63/// `QEventLoop` until the server replies) -- unusable on a WASM main thread,
64/// which Qt refuses to spin a nested loop on at all. `registerModelAsync()`
65/// is the non-blocking alternative `Bridge::registerHandler()` prefers when
66/// available (see `IBackend::registerModelAsync`'s doc comment): it assigns a
67/// call-id, sends the message, returns immediately, and invokes exactly one
68/// of its `onRegistered`/`onError` callbacks once the matching reply arrives
69/// -- the same call-id-matching mechanism `execute()` already uses.
70/// `deregisterModel()` is fire-and-forget (it sends the message without
71/// waiting, avoiding a nested event loop during destruction). `execute()` is
72/// asynchronous: it assigns a call-id, sends the message, and resolves the
73/// returned `Completion` when the matching reply arrives.
74///
75/// @par TLS
76/// Pass a `QSslConfiguration` to enable `wss://`. Build it with `tlsVerifyingConfig()`
77/// (CA-verified — the recommended production default) or `tlsPinnedConfig()`
78/// (pinned-certificate — the correct choice for a self-signed deployment), both in
79/// `qt_tls.hpp`. `tlsInsecureNoVerify()` disables peer verification entirely and is
80/// for local development and tests only — see security.md's "Transport security" section.
81///
82/// @par SSL-less Qt builds (`QT_NO_SSL`, including the standard Qt-for-WebAssembly build)
83/// The constructor's `tls` parameter (and the `_tls` member) does not exist at all
84/// when Qt itself was configured without SSL — `QSslConfiguration` isn't a type
85/// Qt provides in that configuration, so there is no value to accept or ignore.
86/// `wss://` still works on such a build regardless: in a WASM/browser
87/// deployment the browser terminates TLS before Qt's `QWebSocket` ever sees
88/// the connection, so the only thing genuinely unavailable is the ability to
89/// *configure* TLS from C++ (client certificates, pinning, etc.) — plain
90/// `wss://` and `ws://` both still connect normally.
91///
92/// @par Threading
93/// Must be used from the Qt event loop thread. `execute()` and the internal
94/// message handler are both called on that thread.
95class QtWebSocketBackend : public ::morph::backend::detail::IBackend {
96public:

193 /// @brief Sends a `register` message and returns without blocking; the
194 /// reply is matched later, asynchronously, by `callId`.
195 ///
196 /// The non-blocking counterpart to `registerModel`/`registerModelWithContext`
197 /// (see `IBackend::registerModelAsync`'s doc comment for why this exists):
198 /// `registerModel` blocks the calling thread in a nested `QEventLoop` via
199 /// `sendSync`, which a WASM main thread cannot do at all. This instead
200 /// assigns a fresh `callId` (the same counter `execute()` uses), sends the
201 /// `register` envelope, and returns `true` immediately; the reply is
202 /// matched via `_pendingRegistrations` when `onTextMessage` sees it (no
203 /// protocol change needed — the server already echoes `callId` on every
204 /// reply, `register` included). Exactly one of @p onRegistered / @p onError
205 /// fires, on the Qt event loop thread, once the reply arrives — or never,
206 /// if the socket disconnects first without ever reconnecting and
207 /// `cancelPending` is never called again for this id (a disconnect
208 /// *before* a reconnect calls `cancelPending`, which does invoke @p onError
209 /// — see `cancelPending`'s doc comment).
210 ///
211 /// If the socket has not finished connecting yet, the request is **queued**
212 /// rather than failed: this is exactly the ordering a single-threaded WASM
213 /// client must use, since it can never block waiting for the connection to
214 /// settle (a `BridgeHandler` constructed the moment the backend is wired
215 /// up, before the first `connected` signal). The queued request is sent —
216 /// with a call-id assigned at that point, not now — the moment `connected`
217 /// fires next (first connect included), in FIFO order. If the socket never
218 /// connects at all and the backend is torn down first, the queued entry is
219 /// still resolved: `~QtWebSocketBackend` calls `cancelPending`, which drains
220 /// `_queuedRegistrations` too and invokes @p onError exactly once for each —
221 /// no call-id was ever assigned, but the callback still fires, the same
222 /// guarantee an already-sent (call-id-bearing) registration gets.
223 ///
224 /// @param typeId String type-id of the model to instantiate.
225 /// @param factory Unused — this backend holds no local model to construct;
226 /// the server instantiates the model from `typeId`.
227 /// @param contextKey Stable identity of the new instance; travels in the wire envelope.
228 /// @param onRegistered Invoked with the server-assigned `ModelId` on success.
229 /// @param onError Invoked with a diagnostic message on failure or disconnect.
230 /// @return `true` always — this backend has an async path (`false` is never returned).
231 bool registerModelAsync(const std::string& typeId,
232 std::function<std::unique_ptr<::morph::model::detail::IModelHolder>()> factory,
233 std::string_view contextKey, std::function<void(::morph::exec::detail::ModelId)> onRegistered,
234 std::function<void(const std::string&)> onError) override;

346 /// @brief Sends a `deregister` message fire-and-forget (does not wait for a reply).
347 ///
348 /// No acknowledgement is awaited, which avoids a nested `QEventLoop` during
349 /// destruction (that can trip Qt asserts). Note the server performs no
350 /// connection-scoped cleanup: an undelivered or lost `deregister` leaves the
351 /// model registered on the server indefinitely.
352 ///

354 /// `execute()`/`registerModelAsync()` use (see issue #65): `callId == 0`

357 /// its own stray "ok" reply handed to an unrelated `registerModel`'s

359 /// connection. The reply is tracked in `_pendingDeregisters` purely so it
360 /// can be recognised and dropped in `onTextMessage`; nothing observes it.

496 /// @brief Call-ids of `deregister` envelopes still awaiting their (unused)
497 /// reply (see issue #65).
498 ///
499 /// `deregisterModel` is fire-and-forget: nobody observes the reply, but it
500 /// still needs a real, non-zero `callId` so `onTextMessage` can recognise
501 /// and drop it explicitly, rather than letting it fall through to the
502 /// `callId == 0` branch and collide with a parked `sendSync` waiter. A
503 /// late reply for an id no longer in this set (already dropped, or the
504 /// backend was cancelled/destroyed) is simply ignored — nothing to clean
505 /// up either way.
506 std::unordered_set<uint64_t> _pendingDeregisters;

508 /// @brief One in-flight `assignPrimaryAsync` call, keyed by `callId`.
509 ///
510 /// Mirrors `PendingRegistration`/`_pendingRegistrations`: same `callId`
511 /// namespace and counter, separate map because an `assign` reply is
512 /// matched the same way a `register`/`registerShared` reply is (a bare
