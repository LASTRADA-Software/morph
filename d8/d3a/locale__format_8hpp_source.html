5/// @file render/locale_format.hpp
6/// @brief Locale numeric-entry normalisation for the control edge.
7///
8/// A locale may render and accept e.g. `"1.050,25"`; the payload a
9/// `morph::units::Quantity` field submits is always the canonical exact
10/// `{num, den, dp}` regardless. This header is the one control-edge
11/// conversion step between the two: the exact `Rational`/`Quantity` digit
12/// routines stay entirely locale-free (they only ever see plain
13/// `.`-decimal text), and a renderer calls `normalizeLocaleNumber` once, at
14/// the point text leaves the control, before handing it to those routines.
15///
16/// @par One aggregate, not a row of swappable views
17/// Both functions take a single `NumericLocale` rather than a row of positional
18/// `std::string_view`s. Six adjacent views of the same type are silently
19/// swappable with each other, which is what `bugprone-easily-swappable-parameters`
20/// exists to catch; with the aggregate a call site names each fact
21/// (`{.decimalSeparator = ",", .groupSeparator = "."}`) and no two parameters of
22/// either function share a type. The next locale fact -- a percent sign, an
23/// exponent separator -- is a new defaulted member rather than a seventh
24/// parameter. The two edges taking the *same* type is the point as much as the
25/// naming is: "these two must agree" is structural instead of a convention a
26/// caller can get half right.
27///
28/// @par Separators are strings, not characters
29/// The locale facts are `std::string_view`, because a real locale's separator
30/// is not always one byte. fr-FR groups with U+202F (narrow no-break space) and
31/// several locales use U+00A0 -- three and two UTF-8 bytes respectively. Typed
32/// as `char`, those cannot be expressed at all: the caller can only pass some
33/// single byte that never matches, so a perfectly valid `"1 050,25"` typed by a
34/// French user normalises to `std::nullopt` and the entry is reported
35/// malformed. An empty view means "this locale has no such separator".
36///
37/// @par So is the negative sign
38/// For the same reason, and measured rather than assumed: of the 711 locales
39/// Qt 6.11.2 knows, 77 report a `negativeSign` that is not a bare ASCII `'-'`.
40/// 23 use U+2212 MINUS SIGN (e.g. eu_ES); 54 more prefix the sign with a bidi
41/// control -- U+061C ARABIC LETTER MARK, U+200E LEFT-TO-RIGHT MARK or U+200F
42/// RIGHT-TO-LEFT MARK -- making it two or three code points, and ar_DZ does so
43/// even though its sign is the ordinary hyphen. Matched as a single `char`,
44/// none of those round-trips as a single `char`: the display edge would emit a
45/// sign the entry edge then rejected. So `negativeSign` is matched as a whole
46/// string too, defaulting to the ASCII `"-"`.
47///
48/// @par And so is the positive sign, on the entry edge only
49/// `normalizeLocaleNumber` reads `NumericLocale::positiveSign` and *drops* what
50/// it matches, because canonical text has no `'+'` in it.
51/// `formatCanonicalNumber` never emits one: a positive number displays unsigned
52/// in every locale, and changing that would alter every positive number the
53/// product shows. So the two functions are inverse across the decimal
54/// separator, the grouping, the digits and the negative sign, but deliberately
55/// not across a positive sign -- entry accepts a spelling display never
56/// produces.
57///
58/// @par The digits are locale data too
59/// `NumericLocale::zeroDigit` is the locale's DIGIT ZERO, and the ten digits
60/// are the ten code points contiguous from it. One base is sufficient rather
61/// than a ten-element table because a Unicode decimal digit set *is* ten
62/// contiguous code points: UAX #44 assigns `Nd` with `Numeric_Value` 0 through
63/// 9 in code point order. Measured over the same 711 locales under Qt 6.11.2,
64/// 76 report a `zeroDigit` other than ASCII `'0'`, across eleven distinct sets:
65/// U+0660 (26 locales), U+06F0 (19), U+1E950 Adlam (12), U+0966 (8), U+09E6
66/// (4), U+11136 Chakma (2), and one each of U+07C0, U+0F20, U+1040, U+1C50 and
67/// U+ABF0. Two of those sets are astral, so a digit is one to four UTF-8 bytes
68/// and the scan decodes a code point rather than comparing a byte.
69///
70/// @par Entry accepts more digit spellings than display emits
71/// `normalizeLocaleNumber` accepts a digit in `[zeroDigit, zeroDigit + 9]` *or*
72/// in `['0', '9']`; `formatCanonicalNumber` emits only the former. That is the
73/// same asymmetry the signs have, applied to digits: an ASCII `'+'` is
74/// accepted in every locale because the locale's own spelling is
75/// on no keyboard, and an ASCII `'5'` is accepted in an `ar_EG` locale for
76/// exactly the same reason. A user with an ASCII keyboard in a native-digit
77/// locale would otherwise be unable to enter a number at all. As with the
78/// positive sign, accepting a spelling display never produces costs nothing:
79/// the canonical output spells every digit in ASCII whatever the input spelled
80/// it, so no *value* can differ. What is not accepted is the two families in
81/// one entry -- see "Digit families do not mix" on `normalizeLocaleNumber`.

90/// @brief The locale facts both control-edge conversions need, in one
91/// designated-initialisable aggregate.
92///
93/// Every member is defaulted to its `"C"`-locale spelling, so a
94/// default-constructed `NumericLocale` is the identity transform in both
95/// directions and a caller naming only the members it cares about gets the
96/// `"C"` spelling for the rest.
97struct NumericLocale {
98 /// The locale's decimal-point string, e.g. `","`. Empty means the locale
99 /// has no decimal separator (an integer-only entry).
100 std::string_view decimalSeparator = ".";
101 /// The locale's digit-grouping string, e.g. `"."` or U+202F. Empty means
102 /// the locale does not group.
103 std::string_view groupSeparator;
104 /// The locale's negative-sign string, e.g. `"\u2212"`. Empty is read as the
105 /// ASCII `"-"`, not as "this entry cannot be negative".
106 std::string_view negativeSign = "-";
107 /// The locale's positive-sign string, e.g. `"\u061c+"`. Entry-edge only:
108 /// it is accepted and dropped, never emitted. Empty leaves the ASCII `"+"`
109 /// as the only accepted spelling.
110 std::string_view positiveSign = "+";
111 /// The locale's DIGIT ZERO, e.g. `"\u0660"`. The ten digits are the ten
112 /// code points contiguous from it. Empty, or not a well-formed UTF-8 code
113 /// point, is read as the ASCII `"0"`.
114 std::string_view zeroDigit = "0";
115};

119/// @brief One decoded UTF-8 code point: its value and how many bytes it took.
120struct CodePoint {
121 /// The decoded scalar value; meaningless when @ref length is `0`.
122 char32_t value = 0;
123 /// The number of bytes consumed, or `0` when the input does not begin with
124 /// a well-formed UTF-8 sequence.
125 std::size_t length = 0;
126};
127
128/// @brief Decodes the UTF-8 sequence at the start of @p text.
129///
130/// Strict: an overlong encoding, a surrogate code point, a truncated sequence
131/// and a stray continuation byte all report a `CodePoint::length` of `0`
132/// rather than some salvaged value. That strictness is load-bearing rather than
133/// pedantic. The digit test below is a *range* test on the decoded value, so a
134/// lenient decoder that let the overlong `C0 B5` through would read it as
135/// U+0035 and accept it as the digit `'5'` -- including in the default ASCII
136/// locale, where that input is not a digit at all.
137/// @param text The remainder of the entry, starting at the scan position.
138/// @return The decoded code point, or a `length` of `0` when @p text does not
139/// start with a well-formed sequence.
140[[nodiscard]] inline CodePoint decodeUtf8(std::string_view text) {
141 if (text.empty()) {
142 return {};
143 }
144 auto const lead = static_cast<unsigned char>(text.front());
145 if (lead < 0x80U) {
146 return {.value = lead, .length = 1};
147 }
148
149 std::size_t length = 0;
150 char32_t value = 0;
151 char32_t least = 0; // the smallest value this length may legally encode
152 if ((lead & 0xE0U) == 0xC0U) {
153 length = 2;
154 value = lead & 0x1FU;
155 least = 0x80;
156 } else if ((lead & 0xF0U) == 0xE0U) {
157 length = 3;
158 value = lead & 0x0FU;
159 least = 0x800;
160 } else if ((lead & 0xF8U) == 0xF0U) {
161 length = 4;
162 value = lead & 0x07U;
163 least = 0x10000;
164 } else {
165 return {}; // a continuation byte or a 5+ byte lead: not a lead byte
166 }
167 if (text.size() < length) {
168 return {}; // truncated
169 }
170 for (std::size_t k = 1; k < length; ++k) {
171 // k is bounded by the size check above.
172 // NOLINTNEXTLINE(cppcoreguidelines-pro-bounds-avoid-unchecked-container-access)
173 auto const cont = static_cast<unsigned char>(text[k]);
174 if ((cont & 0xC0U) != 0x80U) {
175 return {}; // not a continuation byte
176 }
177 value = (value << 6U) | (cont & 0x3FU);
178 }
179 constexpr char32_t kMaxScalar = 0x10FFFF;
180 constexpr char32_t kSurrogateFirst = 0xD800;
181 constexpr char32_t kSurrogateLast = 0xDFFF;
182 if (value < least || value > kMaxScalar || (value >= kSurrogateFirst && value <= kSurrogateLast)) {
183 return {}; // overlong, out of range, or a surrogate
184 }
185 return {.value = value, .length = length};
186}

188/// @brief Appends @p value to @p out as UTF-8.
189/// @param out The string to append to.
190/// @param value A scalar value; callers here only ever pass a digit derived
191/// from a `zeroDigit` that `decodeUtf8` already validated.
192inline void appendUtf8(std::string& out, char32_t value) {
193 constexpr char32_t kContMask = 0x3F;
194 constexpr unsigned kContShift = 6;
195 auto const byte = [&out](char32_t bits) { out += static_cast<char>(bits); };
196 if (value < 0x80) {
197 byte(value);
198 } else if (value < 0x800) {
199 byte(0xC0U | (value >> kContShift));
200 byte(0x80U | (value & kContMask));
201 } else if (value < 0x10000) {
202 byte(0xE0U | (value >> (2 * kContShift)));
203 byte(0x80U | ((value >> kContShift) & kContMask));
204 byte(0x80U | (value & kContMask));
205 } else {
206 byte(0xF0U | (value >> (3 * kContShift)));
207 byte(0x80U | ((value >> (2 * kContShift)) & kContMask));
208 byte(0x80U | ((value >> kContShift) & kContMask));
209 byte(0x80U | (value & kContMask));
210 }
211}

213/// @brief Appends one character of canonical text to a display string, with a
214/// digit rewritten into the locale's set.
215///
216/// Anything that is not an ASCII digit is copied through verbatim. That arm is
217/// not dead code for a caller that honours the contract, but it is what bounds
218/// the damage for one that does not: a `"12.34.56"` handed to the display edge
219/// keeps its second `'.'` rather than becoming some code point below the digit
220/// base. Only digits are rewritten; text that has none passes through.
221/// @param out The display string to append to.
222/// @param base The locale's DIGIT ZERO code point (see `digitBase`).
223/// @param chr One byte of canonical text.
224inline void appendDisplayDigit(std::string& out, char32_t base, char chr) {
225 if (chr >= '0' && chr <= '9') {
226 appendUtf8(out, base + static_cast<char32_t>(chr - '0'));
227 } else {
228 out += chr;
229 }
230}

232/// @brief How many bytes @p value occupies in UTF-8.
233/// @param value A scalar value.
234/// @return `1`, `2`, `3` or `4`.
235[[nodiscard]] inline std::size_t utf8Length(char32_t value) {
236 if (value < 0x80) {
237 return 1;
238 }
239 if (value < 0x800) {
240 return 2;
241 }
242 if (value < 0x10000) {
243 return 3;
244 }
245 return 4;
246}

248/// @brief The code point of @p zeroDigit, or `U'0'` when it is empty or not a
249/// well-formed UTF-8 code point.
250///
251/// Empty reads as the ASCII `'0'` for the reason an empty `negativeSign` reads
252/// as `'-'`: there is no locale without digits, so empty cannot mean absence,
253/// and a base of "nothing" would reject every entry the locale can produce.
254/// Only the first code point is read; anything after it is locale data this
255/// function has no use for.
256/// @param zeroDigit The locale's DIGIT ZERO spelling.
257/// @return The base code point of the locale's digit set.
258[[nodiscard]] inline char32_t digitBase(std::string_view zeroDigit) {
259 CodePoint const decoded = decodeUtf8(zeroDigit);
260 return decoded.length == 0 ? U'0' : decoded.value;
261}

263/// @brief A digit matched at the start of an entry.
264struct DigitMatch {
265 /// The number of bytes the digit occupies; `0` when there is no digit there.
266 std::size_t length = 0;
267 /// The canonical ASCII spelling of the digit's value, `'0'`-`'9'`.
268 char canonical = '0';
269 /// Whether the match came from the locale's own digit set rather than from
270 /// the ASCII set every locale additionally accepts. When @p base is `U'0'`
271 /// the two sets coincide and this is always `true`.
272 bool native = false;
273};

275/// @brief Matches a digit at the start of @p rest, in the locale's set or in
276/// ASCII.
277///
278/// A function of its own for the reason `leadingSign` is: the normalising scan
279/// reads as one statement per character class, and folding the two digit
280/// families plus the UTF-8 decode into it took it over clang-tidy's cognitive
281/// complexity threshold.
282/// @param rest The remainder of the entry, starting at the scan position.
283/// @param base The locale's DIGIT ZERO code point (see `digitBase`).
284/// @return The match, or a `length` of `0` when @p rest starts with no digit.
285[[nodiscard]] inline DigitMatch leadingDigit(std::string_view rest, char32_t base) {
286 CodePoint const decoded = decodeUtf8(rest);
287 if (decoded.length == 0) {
288 return {};
289 }
290 if (decoded.value >= base && decoded.value < base + 10) {
291 return {
292 .length = decoded.length, .canonical = static_cast<char>(U'0' + (decoded.value - base)), .native = true};
293 }
294 if (decoded.value >= U'0' && decoded.value <= U'9') {
295 // The ASCII spelling, accepted in every locale for the reason the ASCII
296 // '-' and '+' are: the locale's own digits are on the user's keyboard
297 // only if their keyboard has them.
298 return {.length = decoded.length, .canonical = static_cast<char>(decoded.value), .native = false};
299 }
300 return {};
301}

303/// @brief Whether every group separator in @p text sits where a group
304/// separator can legally sit.
305///
306/// The rule, in one place so it can be read on its own: a group separator is
307/// preceded by one to three digits (the first group), or by exactly three
308/// (every later one); it is followed by exactly three more digits, at each
309/// group and at the end of the integer part; and it never appears after the
310/// decimal separator. A locale with no grouping (an empty
311/// `NumericLocale::groupSeparator`) has nothing to place, so it trivially
312/// passes.
313///
314/// This is a pass of its own rather than extra state inside the normalising
315/// scan below: "the grouping is well placed" and "the digits convert" are two
316/// separate statements about the entry, and reading them as one made neither
317/// clear.
318///
319/// It counts *digits*, not bytes, in the locale's set as well as in ASCII. A
320/// byte-by-byte scan is only correct while a digit is one byte: a two-byte
321/// U+0665 would reset the run-length counter on its own continuation byte, so
322/// `"\u0661\u066c\u0660\u0665\u0660"` -- what `formatCanonicalNumber` emits
323/// for `1050` in an `ar_EG` locale -- would be rejected as badly grouped and the
324/// pair would not round-trip.
325///
326/// Characters this function does not recognise are simply not digits — the
327/// normalising scan is what rejects them, and it rejects them whatever this
328/// pass concludes.
329/// @param text The locale-formatted entry.
330/// @param loc The locale facts; only the two separators and the digit base are
331/// read.
332/// @return `true` when the grouping is well placed (or absent).
333[[nodiscard]] inline bool groupingIsWellPlaced(std::string_view text, NumericLocale const& loc) {
334 if (loc.groupSeparator.empty()) {
335 return true;
336 }
337 constexpr std::size_t kGroupSize = 3;
338 char32_t const base = digitBase(loc.zeroDigit);
339 std::size_t digits = 0;
340 bool sawGroup = false;
341 bool sawDecimal = false;
342
343 for (std::size_t i = 0; i < text.size();) {
344 const std::string_view rest = text.substr(i);
345 if (rest.starts_with(loc.groupSeparator)) {
346 bool const opensAGroup = sawGroup ? digits == kGroupSize : (digits >= 1 && digits <= kGroupSize);
347 if (sawDecimal || !opensAGroup) {
348 return false;
349 }
350 sawGroup = true;
351 digits = 0;
352 i += loc.groupSeparator.size();
353 continue;
354 }
355 if (!loc.decimalSeparator.empty() && rest.starts_with(loc.decimalSeparator)) {
356 if (sawGroup && digits != kGroupSize) {
357 return false; // the last group of the integer part is short
358 }
359 sawDecimal = true;
360 digits = 0;
361 i += loc.decimalSeparator.size();
362 continue;
363 }
364 DigitMatch const digit = leadingDigit(rest, base);
365 digits = digit.length != 0 ? digits + 1 : 0;
366 i += digit.length != 0 ? digit.length : 1;
367 }
368
369 // An ungrouped fractional part ends the number, so the trailing check only
370 // applies when the integer part was the last thing scanned.
371 return !sawGroup || sawDecimal || digits == kGroupSize;
372}

374/// @brief The length of @p separator at the start of @p rest, in bytes, or `0`
375/// when it is not there -- or is empty.
376///
377/// The empty case is why this is a function and not an inline `starts_with`:
378/// `rest.starts_with("")` is `true` at every index, so an empty separator
379/// matched inline would swallow the whole entry one zero-length step at a time.
380/// Spelling the guard as `!sep.empty() && ...` at each call site instead adds
381/// two conjunctions to `normalizeLocaleNumber`, which is enough to put it over
382/// clang-tidy's cognitive-complexity threshold.
383/// @param rest The remainder of the entry, starting at the scan position.
384/// @param separator The locale's spelling of this separator; empty means the
385/// locale has none, and matches nothing.
386/// @return The number of bytes the separator occupies, or `0`.
387[[nodiscard]] inline std::size_t leadingSeparatorLength(std::string_view rest, std::string_view separator) {
388 return !separator.empty() && rest.starts_with(separator) ? separator.size() : 0U;
389}

391/// @brief The length of a sign at the start of @p rest, in bytes, or `0` when
392/// there is none there.
393///
394/// Two spellings count. @p localeSign is the locale's own, matched as a whole
395/// string so that U+2212 and the bidi-control-prefixed forms -- two and three
396/// code points -- match at all; a single `char` can express none of them.
397/// @p asciiSign counts as well, in every locale: U+2212
398/// and the bidi marks are on no keyboard, so matching only the locale's
399/// spelling would reject the sign the user can actually type. Neither `'-'` nor
400/// `'+'` has a second reading in a numeric entry, so this is not the kind of
401/// guess the grouping rule forbids.
402///
403/// This is a function of its own so that the caller's scan reads as one
404/// statement per character class. It is shared by both signs and says nothing
405/// about what the caller then emits, which differs between them: a negative is
406/// emitted as the canonical `'-'`, a positive is dropped (see
407/// `normalizeLocaleNumber`).
408/// @param rest The remainder of the entry, starting at the scan position.
409/// @param localeSign The locale's spelling of this sign; empty matches nothing,
410/// leaving only the ASCII spelling.
411/// @param asciiSign The ASCII spelling accepted in every locale: `'-'` or `'+'`.
412/// @return The number of bytes the sign occupies, or `0`.
413[[nodiscard]] inline std::size_t leadingSignLength(std::string_view rest, std::string_view localeSign,
414 char asciiSign) {
415 if (!localeSign.empty() && rest.starts_with(localeSign)) {
416 return localeSign.size();
417 }
418 return rest.starts_with(asciiSign) ? 1U : 0U;
419}

421/// @brief A sign matched at the start of an entry: how much of the text it
422/// occupies, and what it contributes to the canonical output.
423struct SignMatch {
424 /// The number of bytes the sign occupies; `0` when there is no sign there.
425 std::size_t length = 0;
426 /// What the canonical text gains: `"-"` for a negative, empty for a
427 /// positive, which is accepted and dropped.
428 std::string_view emits;
429};

431/// @brief Matches either sign at the start of @p rest.
432///
433/// Both signs in one function, and the emitted text carried back with the
434/// length, so the normalising scan below has a *single* sign branch with no
435/// inner "which sign was it" test. That is not only tidier: two branches with
436/// two inner tests each put `normalizeLocaleNumber` at a cognitive complexity
437/// of 28, over clang-tidy's threshold of 25; with the single branch it sits at
438/// 23. The asymmetry between the two signs lives here, in the one place that
439/// decides it, rather than in the scan.
440///
441/// The negative sign is tried first. The order is not load-bearing for any
442/// locale Qt 6.11.2 reports -- `starts_with` is an exact prefix match and no
443/// locale spells one sign as a prefix of the other -- but it is fixed here so
444/// that it cannot vary.
445/// @param rest The remainder of the entry, starting at the scan position.
446/// @param loc The locale facts; only the two signs are read. An empty
447/// `negativeSign` leaves `'-'`, an empty `positiveSign` leaves
448/// `'+'`.
449/// @return The match, or a `length` of `0` when @p rest starts with no sign.
450[[nodiscard]] inline SignMatch leadingSign(std::string_view rest, NumericLocale const& loc) {
451 std::size_t const negativeLength = leadingSignLength(rest, loc.negativeSign, '-');
452 if (negativeLength != 0) {
453 // The canonical spelling, whatever the locale's is.
454 return {.length = negativeLength, .emits = "-"};
455 }
456 // Dropped, never emitted: canonical text is `-?[0-9]+(\.[0-9]+)?` and has
457 // no `+` in it.
458 return {.length = leadingSignLength(rest, loc.positiveSign, '+'), .emits = ""};
459}

463/// @brief Converts a locale-formatted numeric string to canonical
464/// (`-?[0-9]+(\.[0-9]+)?`) text.
465///
466/// Drops `NumericLocale::groupSeparator` where it is correctly placed, replaces
467/// every occurrence of `NumericLocale::decimalSeparator` with `.`, and rewrites
468/// the locale's digits as ASCII ones. A default-constructed `NumericLocale` is
469/// the identity transform (the locale-free behavior). Malformed input (a second
470/// decimal separator, a sign anywhere but the leading position of the *output*,
471/// two digit families in one entry, or any character that is not a digit)
472/// yields `std::nullopt` rather than a best-effort guess. The decimal point
473/// counts as output, so a sign placed straight after the separator ("`,-5`" in
474/// a de-DE locale) is rejected -- matching the QML mirror in
475/// `src/qt/forms/qml/DynamicForm.qml`, which rejects it too.
476///
477/// @par Grouping is validated, not stripped
478/// A group separator is only dropped where a group separator can legally be:
479/// preceded by one to three digits, followed by exactly three more, and never
480/// after the decimal separator. Anything else is malformed and reported as
481/// such. Stripping unconditionally instead yields a wrong *value*, not a
482/// rejected one, and nothing downstream can tell: a de-DE user typing the US
483/// form `"1.5"` into a price field would submit `15` -- a perfectly valid
484/// number, ten times too large. `"1.50"` would give `150`, `"1.2.3.4"` would
485/// give `1234`, and the en-US mirror image `"1,5"` would give `15`.
486///
487/// @par The two separators must differ
488/// When `groupSeparator` is non-empty and equal to `decimalSeparator` the entry
489/// is rejected: with one string in both roles there is no reading of `"1.5"`
490/// the function could defend. This is a caller (locale-configuration) error
491/// rather than a user one, but it is reported through the return value like any
492/// other malformed entry, deliberately not through an assertion -- an assertion
493/// would make the two build configurations behave differently at a control
494/// edge, and would be untestable in the one where it fires.
495///
496/// The result is `.`-decimal and digit-only, but is **not** narrowed to
497/// `-?[0-9]+(\.[0-9]+)?`: a bare "`.`", a leading "`.5`" and a trailing "`5.`"
498/// are passed through, exactly as that same QML mirror passes them. Tightening
499/// one side alone would put the two control edges out of step, so the shape is
500/// documented here rather than narrowed.
501///
502/// Separators are matched as whole strings, so a multi-byte one (e.g. U+202F)
503/// works; matching them before the digit scan is what keeps their continuation
504/// bytes from being mistaken for stray non-digit characters.
505///
506/// @par The negative sign is matched as a whole string too
507/// `negativeSign` is matched the same way, which is what lets a locale whose
508/// sign is U+2212, or is prefixed by a bidi control mark, be entered at all --
509/// 77 of the 711 locales Qt 6.11.2 knows. Matched as a literal byte `'-'`
510/// instead, `formatCanonicalNumber` would emit a sign this function rejected
511/// and the pair would not be inverse for those locales.
512///
513/// @par ASCII `'-'` stays accepted whatever the locale
514/// A bare `'-'` is accepted in the leading position in addition to
515/// `negativeSign`. U+2212 and the bidi marks are on no keyboard, so matching
516/// only the locale's own spelling would reject the sign the user can actually
517/// type and leave them no way to enter a negative number at all. The hyphen has
518/// no second reading in a numeric entry, so accepting it is not the kind of
519/// guess the grouping rule forbids -- that one is about producing a wrong
520/// *value*, and this produces the only value the input can mean.
521///
522/// @par An empty `negativeSign` means the ASCII default, not "no sign"
523/// Unlike a group separator, there is no locale without a negative sign, so an
524/// empty view leaves the ASCII `'-'` above as the only spelling rather than
525/// meaning "this entry cannot be negative". `formatCanonicalNumber` reads it
526/// the same way, and the display edge is why it must: a sign that formatted to
527/// nothing would turn `-5` into `5` silently -- a wrong value, not a rejected
528/// one.
529///
530/// @par A leading positive sign is accepted and dropped
531/// `positiveSign` is matched exactly like `negativeSign` -- the locale's own
532/// spelling as a whole string, plus a bare ASCII `'+'` in every locale. Of the
533/// 711 locales Qt 6.11.2 knows, 54 spell it as more than one code point
534/// (U+061C, U+200E or U+200F before the `'+'`, e.g. `ar_EG`, `ar_DZ`, `az_IR`,
535/// `ckb_IQ`); the other 657 use the bare `'+'`. Unlike the negative side there
536/// is no U+2212 analogue, so *every* non-ASCII spelling here is multi-code-point
537/// and whole-string matching is the only thing that can match any of them.
538/// Without this branch a leading `'+'` falls through to the "any other
539/// character is malformed" arm, and an explicitly-positive entry is rejected in
540/// every locale, `"C"` included.
541///
542/// @par The sign is **dropped**, and `formatCanonicalNumber` never emits one
543/// This is a deliberate asymmetry with the negative sign, not an oversight.
544/// Canonical text is `-?[0-9]+(\.[0-9]+)?`: there is no `'+'` in it, so `"+5"`
545/// yields `"5"` and not `"+5"`. The display edge reads no `positiveSign` at
546/// all, because emitting one would change what every positive number in every
547/// form looks like -- `5` would become `+5` on screen. So the two functions are
548/// *not* strict inverses across a positive sign: entry accepts a spelling
549/// display never produces. That is the only shape that adds acceptance without
550/// changing a single rendered value. Written down in `docs/spec/forms/forms.md`
551/// as well, under "Locale data formatting".
552///
553/// @par An empty `positiveSign` leaves the ASCII `'+'`
554/// Here empty really can mean "match nothing extra", because there is no
555/// display edge to get wrong: the worst an unmatched positive sign can do is
556/// reject an entry, never produce a value of the wrong sign. The bare ASCII
557/// `'+'` stays accepted regardless.
558///
559/// @par The locale's own digits are accepted, and so are ASCII ones
560/// A digit is accepted when its code point is in
561/// `[zeroDigit, zeroDigit + 9]` -- a Unicode decimal digit set is ten
562/// contiguous code points by definition (UAX #44) -- *or* in `['0', '9']`. 76
563/// of the 711 locales Qt 6.11.2 knows use a non-ASCII `zeroDigit`; without the
564/// first acceptance their users could not enter a number at all, because a scan
565/// comparing a single byte against the ASCII range fails on the very first byte
566/// of U+0665. The second acceptance is the same rule as the ASCII `'-'` and
567/// `'+'` above, for the same reason: a user with an ASCII keyboard in an
568/// `ar_EG` locale has to be able to type `5`. It costs nothing, because the
569/// canonical output spells every digit in ASCII whatever the input spelled it,
570/// so no two accepted spellings can produce different *values*.
571///
572/// @par Digit families do not mix
573/// `"\u06655"` -- one Arabic-Indic digit and one ASCII digit -- is malformed,
574/// not `"55"`. The two families are each accepted whole; interleaving them is
575/// not a spelling any keyboard or any display edge produces, and rejecting it
576/// matches the strictness about a sign anywhere but the leading position. It is
577/// a choice rather than a consequence, so it is stated here and pinned by a
578/// test on both edges. When `zeroDigit` is the ASCII `"0"` the two families are
579/// the same set, so nothing can mix and the rule is invisible.
580///
581/// @param text The locale-formatted entry, e.g. `"1.050,25"`.
582/// @param loc The locale facts. Designated initialisers are the intended
583/// spelling: `{.decimalSeparator = ",", .groupSeparator = "."}`.
584/// @return The canonical `.`-decimal text, or `std::nullopt` when malformed.
585[[nodiscard]] inline std::optional<std::string> normalizeLocaleNumber(std::string_view text,
586 NumericLocale const& loc) {
587 if (!loc.groupSeparator.empty() && loc.groupSeparator == loc.decimalSeparator) {
588 return std::nullopt; // one string cannot play both roles: see above
589 }
590 if (!detail::groupingIsWellPlaced(text, loc)) {
591 return std::nullopt; // a separator off a group boundary: see above
592 }
593
594 char32_t const base = detail::digitBase(loc.zeroDigit);
595 std::string canonical;
596 canonical.reserve(text.size());
597 bool sawDecimal = false;
598 bool sawAnyOutput = false;
599 bool sawNativeDigit = false;
600 bool sawAsciiDigit = false;
601
602 for (std::size_t i = 0; i < text.size();) {
603 const std::string_view rest = text.substr(i);
604 if (std::size_t const group = detail::leadingSeparatorLength(rest, loc.groupSeparator); group != 0) {
605 // Placement was settled above, so by here the separator is display
606 // only and is never carried into the output.
607 i += group;
608 continue;
609 }
610 if (std::size_t const point = detail::leadingSeparatorLength(rest, loc.decimalSeparator); point != 0) {
611 if (sawDecimal) {
612 return std::nullopt; // a second decimal separator: malformed
613 }
614 sawDecimal = true;
615 canonical += '.';
616 // The decimal point *is* output: without this, the `sawAnyOutput`
617 // guard in the sign branch below still believes nothing has been
618 // emitted, and a sign placed straight after the separator
619 // ("`,-5`" in a de-DE locale) is accepted as if it were leading.
620 sawAnyOutput = true;
621 i += point;
622 continue;
623 }
624 detail::SignMatch const sign = detail::leadingSign(rest, loc);
625 if (sign.length != 0) {
626 // Leading position of the *output*: a stripped group separator
627 // before the sign would otherwise make an injected sign look
628 // leading. The same rule for both signs, which is why they share a
629 // branch.
630 if (sawAnyOutput) {
631 return std::nullopt; // sign injection past the leading position
632 }
633 // Empty for a positive sign, which is dropped rather than
634 // carried. `sawAnyOutput` is set either way, so "+-5", "++5" and
635 // "1+2" stay malformed: consuming a sign counts as output even when
636 // it contributes no character.
637 canonical += sign.emits;
638 sawAnyOutput = true;
639 i += sign.length;
640 continue;
641 }
642 detail::DigitMatch const digit = detail::leadingDigit(rest, base);
643 if (digit.length == 0) {
644 return std::nullopt; // any other character is malformed
645 }
646 // Which family each digit came from is recorded here and judged once,
647 // below the loop: an entry that mixes them is malformed wherever the
648 // second family appears, so there is nothing an early return would
649 // decide differently, and the scan stays one statement per character
650 // class.
651 (digit.native ? sawNativeDigit : sawAsciiDigit) = true;
652 canonical += digit.canonical;
653 sawAnyOutput = true;
654 i += digit.length;
655 }
656
657 if (sawNativeDigit && sawAsciiDigit) {
658 return std::nullopt; // two digit families in one entry: see above
659 }
660 if (canonical.empty() || canonical == "-") {
661 return std::nullopt;
662 }
663 return canonical;
664}

666/// @brief Converts canonical (`.`-decimal) numeric text to locale-formatted
667/// display text, grouping the integer part in triples.
668///
669/// The display-direction inverse of `normalizeLocaleNumber`'s
670/// decimal-separator substitution and digit rewriting, plus thousands grouping
671/// that `normalizeLocaleNumber` takes back: a grouped display round-trips,
672/// because the entry direction *validates* the grouping rather than stripping
673/// it (see "Grouping is validated, not stripped" on that function). A
674/// default-constructed `NumericLocale` is the identity transform.
675///
676/// The sign is emitted as `NumericLocale::negativeSign`, matching what
677/// `normalizeLocaleNumber` accepts back; an empty view is read as
678/// `"-"` rather than as "no sign", because formatting a negative to no sign at
679/// all is a silently wrong value.
680///
681/// @par The digits are emitted in the locale's set
682/// Each canonical `'0'`-`'9'` is emitted as the code point that far above
683/// `NumericLocale::zeroDigit`, so an `ar_EG` caller sees `"\u0665"` where the
684/// canonical text said `'5'`. This edge has to match the entry edge: entry
685/// accepts U+0665, so display emitting a plain `'5'` would leave the pair not
686/// inverse, and `docs/spec/forms/forms.md` requires that round trip. With the
687/// default `zeroDigit` of `"0"` the offset is zero and the canonical ASCII
688/// bytes are copied out unchanged.
689///
690/// @par There is no positive-sign emission, deliberately
691/// A positive number is displayed with no sign at all, in every locale, and
692/// this function ignores `NumericLocale::positiveSign` entirely.
693/// `normalizeLocaleNumber` *accepts* a leading positive sign and drops it, so
694/// the pair is not a strict inverse across one: entry takes a spelling display
695/// never produces. Emitting it is what would be the defect --
696/// `QLocale::positiveSign()` is `'+'` in 657 of the 711 locales Qt 6.11.2
697/// knows, so emitting it would turn every positive number in every form from
698/// `5` into `+5`, a visible product change with no need behind it. The failure
699/// this pair guards against is one edge producing text the other rejects;
700/// emitting a sign nothing asks for would create exactly that.
701/// @param canonicalText Canonical `-?[0-9]+(\.[0-9]+)?` text.
702/// @param loc The locale facts; `positiveSign` is not read.
703/// @return The locale-formatted display text.
704[[nodiscard]] inline std::string formatCanonicalNumber(std::string_view canonicalText, NumericLocale const& loc) {
705 constexpr std::size_t kGroupSize = 3;
706 char32_t const base = detail::digitBase(loc.zeroDigit);
707 bool const neg = !canonicalText.empty() && canonicalText.front() == '-';
708 std::string_view const magnitude = neg ? canonicalText.substr(1) : canonicalText;
709 auto const dot = magnitude.find('.');
710 std::string_view const wholePart = dot == std::string_view::npos ? magnitude : magnitude.substr(0, dot);
711 std::string_view const fracPart = dot == std::string_view::npos ? std::string_view{} : magnitude.substr(dot + 1);
712
713 // A digit of the locale's set is one to four UTF-8 bytes, so the reserve
714 // hint scales with the base rather than assuming one byte per digit.
715 std::size_t const perDigit = detail::utf8Length(base);
716 std::string out;
717 out.reserve(loc.negativeSign.size() + (magnitude.size() * perDigit) +
718 ((wholePart.size() / kGroupSize) * loc.groupSeparator.size()) + loc.decimalSeparator.size());
719
720 if (neg) {
721 out += loc.negativeSign.empty() ? std::string_view{"-"} : loc.negativeSign;
722 }
723 std::size_t index = 0;
724 for (char const chr : wholePart) {
725 if (!loc.groupSeparator.empty() && index != 0 && (wholePart.size() - index) % kGroupSize == 0) {
726 out += loc.groupSeparator;
727 }
728 detail::appendDisplayDigit(out, base, chr);
729 ++index;
730 }
731 if (!fracPart.empty()) {
732 out += loc.decimalSeparator;
733 for (char const chr : fracPart) {
734 detail::appendDisplayDigit(out, base, chr);
735 }
736 }
737 return out;
738}
