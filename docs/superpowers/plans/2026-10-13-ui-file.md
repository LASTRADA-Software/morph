# The file side channel: implementation plan (part 9 B2, #894)

**Goal.** A document uploads a file the user picked and downloads a file a reply referenced, through the UI
service's `ui-file` kind, in chunks, with progress. Authorisation follows spec 5 §12 and the decision recorded on
#894: an upload is authorised as the mutation that will reference it; a download is authorised by presenting a
principal-bound capability reference.

**Specs.** Spec 6 §18 (`files/1`), spec 5 §9 (`upload`, `download` commands), §12 (`ui-file`). In-tree:
`docs/spec/ui/service.md`, `include/morph/ui/service.hpp`, `include/morph/ui/service_client.hpp`,
`include/morph/ui/interpreter.hpp` (`InterpreterHost::upload`/`download`, the `upload` command).

## What planning found

1. **The interpreter does not tell the host which mutation an upload is for.** `{"upload": e, "to": "m"}` calls
   `InterpreterHost::upload(file, progress, done)` and, on the reference, runs mutation `m` with it in the body. An
   upload authorised as `m` needs `m`'s model type and action at the start of the transfer. The interpreter gains an
   `UploadRequest` (the file, the model type, the action) and an `upload(UploadRequest, …)` overload whose default
   calls the existing one, so hosts that override the old signature keep working.
2. **Reading a picked file is the platform's.** A `filePicker` hands the document an opaque local reference; only
   the host can turn it into bytes (a path on the desktop, a `File` in the browser). The client helper therefore
   takes a reader, `std::function<std::expected<std::string, std::string>(Value const& file)>`, and the chunking,
   progress and envelope exchange are the framework's.
3. **The download reference is issued by the application.** A model that returns a file puts a reference in its
   reply. The store issues it for the principal the reply is for: `IFileStore::issue(principal, name, type, bytes)`.
   The model does not know the principal (a model does not know the framework exists), so issuing happens in the
   server's own layer, which an application wires: a handler or an `IEnvelopeService` that owns both. (B2 ships the
   store and the kind; how an application threads the principal into a reply that issues references is documented,
   not automated.)

## Design

### The store (`ui/file_store.hpp`)

- `IFileStore`: `begin(principal, name, type, size) -> uploadId`, `append(principal, uploadId, offset, bytes)`,
  `finish(principal, uploadId) -> FileRef`, `issue(principal, name, type, bytes) -> FileRef`,
  `read(principal, ref, offset, length) -> {bytes, total, name, type}`. Every call takes the principal and refuses a
  mismatch: an upload id and a reference belong to the principal that created them.
- `FileRef` is `file:` followed by 32 lower-case hex digits read straight from `std::random_device` (not used as a
  seed): libstdc++, libc++ and MSVC back it with the operating system's entropy source, so the reference is
  unguessable, and holding it is the capability. The repository has no CSPRNG helper; the WebSocket key's
  `mt19937` is not one.
- `MemoryFileStore`: the default, bounded by `maxBytesPerPrincipal` and `maxFileBytes`; an unfinished upload expires
  after `uploadTtl`. A deployment that persists files implements `IFileStore`.

### The kind (`ui-file`, in `UiService`)

One kind, an `op` in the body:

| `op` | Request | Reply | Gate |
|---|---|---|---|
| `begin` | `{name, type, size, model, action}` | `{upload}` | `authorize(session, model, action)`: as the mutation that will reference it |
| `chunk` | `{upload, offset, data}` (base64url, `session::detail::base64UrlEncode`) | `{received}` | the upload id belongs to the principal |
| `end` | `{upload}` | `{ref}` | the upload id belongs to the principal; every byte received |
| `read` | `{ref, offset, length}` | `{data, total, name, type}` | the reference belongs to the principal |

- A chunk is at most `kMaxFileChunkBytes` (256 KiB of payload, about 342 KiB of base64), well under
  `wire::kMaxEnvelopeBytes`; `offset` must equal the bytes received so far, so a chunk is never applied twice or out of
  order.
- An unknown or foreign upload id or reference is `err "not found"`: a caller cannot tell a reference that exists
  for someone else from one that does not exist.

### The client (`ui/service_client.hpp`)

- `FileTransfer` over `Exchange` and a session: `upload(UploadRequest, reader, progress, done)` and
  `download(ref, progress, done)`, each a sequence of `ui-file` requests, one chunk in flight at a time. Progress
  is reported after each chunk; a failure ends the transfer with its reason.
- A host's `InterpreterHost::upload`/`download` delegates to it; `DocumentScreenHost` (#933) can forward to one
  when given.

## Verification

Each gate fails its test when removed: `begin` without the action's authorisation, a chunk at a wrong offset, a
foreign upload id, a foreign reference. A transfer larger than one chunk is measured as more than one exchange.
