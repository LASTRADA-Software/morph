# The One Table, and Editing in It — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the table of `docs/spec/table/table.md`, a table as a run-time description any model offers, one pipeline for every surface, slow columns and their caches, configuration, persisted state and acting on rows, and the editing of `docs/spec/table/editing.md`, grids of forms, cells of a model's table and the layouts entry grids need. Along the way, remove paging in a database.

**Architecture:** The table engine (`include/morph/table`) gains the description, unloaded cells, levels, the level and view caches, column groups, values with units and row selections; the UI layer (`include/morph/ui`) gains `TableRows` with its two implementations, cell formatting, the column window, the configuration menus, persisted state and grids; the forms engine gains derived values and per-cell snapshots. Every task follows the spec's **Delivery order** (table.md steps 0 to 9c, then editing.md steps 1 to 6), and each lands with the tests and mutations the spec's **Tests** tables name.

**Tech Stack:** C++23, CMake (Ninja, MSVC preset `cl-debug`), header-only morph, glaze, Catch2, Qt 6 Quick (offscreen test executables only), the terminal backend, Qt WebAssembly (single-threaded) for the browser gates.

**Spec:** `docs/spec/table/table.md` and `docs/spec/table/editing.md`. Each task quotes the section it implements; the executor reads that section before writing a line. Where this plan and the spec differ, the spec wins and the plan is corrected.

## Global Constraints

- AGENTS.md "Comments and documentation": a comment or spec states what the code does now and why; no history, no issue numbers, no commit hashes.
- Every public symbol has complete Doxygen `@param`/`@tparam`/`@return`; the docs build runs `WARN_AS_ERROR = FAIL_ON_WARNINGS` (`cmake -S . -B build/doc -G Ninja -DMORPH_BUILD_DOCUMENTATION=ON -DMORPH_BUILD_TESTS=OFF -DMORPH_BUILD_EXAMPLES=OFF && cmake --build build/doc --target doc`).
- morph is public: no company, product or customer names in code, tests, specs or commit messages; examples use the neutral `lims` domain.
- Commits are authored `yaraslau <mail@yaraslau.com>` and end with the session's attribution lines.
- No GUI application is launched by hand or by an agent; Qt Quick behaviour is tested through `morph_qt_quick_tests` (offscreen).
- AGENTS.md "Verify rather than assert": every test names the mutation it was seen to fail on, and the task runs that mutation once and records the failing output in its commit message body.
- Limits are the spec's, verbatim: `Virtualization{threshold = 2000, overscan = 10, columnThreshold = 40, cellThreshold = 20'000, columnOverscan = 4, realizePerFrame = 240}`; `QueryLimits::maxColumns = 512`, `maxKeys = 1000`, `maxSetValues = 10'000`, `maxQuerySetValues = 20'000`, `maxQuerySetBytes = 1 MiB`, `maxGroupColumns = 16`, `maxSortKeys = 8` (up to 32 by `limits`), `maxSelectedRows = 1'000'000`, `maxRetained = 10'000`; `SessionOptions::maxRangeRows = 10'000`, `maxCopyRows = 10'000`, `maxPasteCells = 10'000`, `tableStateTimeout = 300 ms`, `tableStateDebounce = 500 ms`, `retainHold = 2 s`; `TableStateOptions::segmentBytes = 12 KiB`; `PageWindow(pageSize = 200, maxPages = 8, maxKeys = 1000, maxColumns = 96)`; a form's `deriveDebounce` default 150 ms.
- A spec that describes code (the "Neighbouring specs" tables of both documents) takes its part in the task whose step its row names, and says nothing of it before.

## The standard task loop

Every task below runs this loop; a task lists only what is specific to it.

1. Read the spec sections the task names, and its rows of the spec's **Tests** table.
2. Write the task's tests (names and assertions as the task gives them, the spec's values in them). Build the test target and run the new cases: they fail, or do not compile, for the reason the task says.
3. Implement the interfaces the task lists, in the files it lists.
4. Run the new cases and the whole target they live in: all pass.
5. Apply each named mutation by hand, run its test, see it fail, revert. Paste the failing line into the commit body.
6. Update the neighbouring specs the task names. Run the docs build when the task adds a public symbol.
7. Commit.

Commands, with `<target>` and `<pattern>` from the task:

```bash
cmake --preset cl-debug                                   # once per tree
cmake --build --preset cl-debug --target <target>
ctest --test-dir build/cl-debug -R "<pattern>" --output-on-failure
```

## Review Focus

1. **A description that changes revision while state is held.** A view selection, retained rows, a focused cell or a cell draft held when the description takes a new revision (a column removed): the client refetches the description, fits its layout, drops what names a removed column, and never sends a query naming it. Test goes to Task 9 ("revision mid-selection").
2. **Negative and boundary values in the display.** `-0.125` at two places under `HalfUp` is `-0.13`, under `HalfEven` `-0.12`; `0` with `empty` set shows `0`, not the empty text; a comma locale with grouping shows `-12.500,50`. Test goes to Task 15.
3. **An empty grid.** A grid over an `ObjectArray` with no rows: the walk with no editable cell lets `Tab` leave at once; a paste into it with `appendRows` adds rows, without it drops everything and says so; summaries over no rows show `count` 0 and an empty `mean`. Tests go to Tasks 19, 21 and 22.
4. **A key change onto a key the client already holds.** A `ChangedRow{key: 7, from: 3}` while row 7 is already held and selected: the selection holds 7 once, and the old row 3 is fetched again. Test goes to Task 17c.
5. **Bands under a stored layout.** A stored layout that hides every column of a band and then shows one again: the band reappears over that one column, with its unit; a band whose columns are all pinned draws only in the pinned part. Test goes to Task 22.
