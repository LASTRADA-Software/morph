# `morph::reactive` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `morph::reactive`, header-only in the base `morph` target: a glitch-free signal graph
(`Signal`, `Computed`, `Effect`, `Scope` over a `Runtime`), `Store<ViewState, Msg>`, declarative control
(`Query`, `Mutation`, `Subscription`, `errorMessage`) and the `Scheduler` it times with, plus the owner test kit
(`StepExecutor`, `OwnerProbeRecorder`) installed under `include/morph/testing/`.

**Architecture:** A push-dirty/pull-value graph (Clean/Check/Dirty) whose nodes share one `detail::RuntimeCore`.
Every write ends a batch; the outermost batch posts **one** flush to the owner executor; the flush pulls queued
Effects through their Computeds, owners first. Misuse is reported through `morph::exec::detail::noteOwner` and then
refused. `Query`, `Mutation` and `Subscription` are signals plus an Effect and a `CallbackScope`, over any
`Completion`-returning fetcher (a `BridgeHandler` in production, a settleable promise in tests).

**Tech Stack:** C++23, header-only; morph core (`IExecutor`, `OwnerAffinity`, `noteOwner`, `Completion`,
`CallbackScope`, `BridgeHandler`); Catch2 v3; Doxygen with `WARN_AS_ERROR`.

**Spec:** `docs/superpowers/specs/2026-10-04-declarative-ui-tui-design.md` (spec 1): §1 "Requirements the reactive
core meets", §2, §3, §4, §4b, §7 "reactive, Store, control", §9. Spec 5
(`docs/superpowers/specs/2026-10-07-ui-document-design.md`) §5 for what a document's queries and mutations need
from this layer: the concurrency modes, `debounce`, `refreshEvery`, and the query cache, which wraps a `Query`'s
fetcher and needs nothing new here. Issue: #887. Program: #885.

**Starting point.** Two older artefacts exist and neither is trusted as is:

- The 2026-10-04 part-1 plan, revised once against spec 1 (`origin/feature/reactive` @ `e3c9ae01`). Its revisions
  R1–R9 are kept below.
- The unreviewed-for-master implementation of that plan on `origin/feature/declarative-ui` @ `d45311e3`. It went
  through eleven review rounds on the old single-branch model (ledger:

**Delivery.** Branch `feature/reactive` from `origin/master`; this plan is its first commit; one commit per task;

## Review Focus

1. **Owner-first effect order.** A queued Effect owned by a scope runs after the queued Effects of the scopes that
   own it, whatever order the writes came in, so a row binding never evaluates against a parent that is about to
   remove it (Task 5, "owner-first").
2. **A flush that falls due inside a widget event** is deferred to the end of the outermost widget event and posted
   then. A nested event loop inside the handler (a modal dialog) neither runs it nor spins on a re-post (Task 2,
   "deferral inside a nested widget event").
3. **A throwing source under a checking observer** errors again on the observer's next read, and an Effect behind
   it runs again on the next change (Task 3).
4. **Re-posting after a throwing Effect is bounded**: at most `maxThrowReposts` flushes in a row; an outside write
   starts a new count (Task 4).
5. **A container of a type without `==`** compiles in a `Signal`, a `Computed` and a `Query` key, and always
   notifies (Task 2).
6. **A Mutation run while another is in flight** does what its `Concurrency` says; the default is `Exclusive`
   (Task 9).
7. **A query destroyed before the mutation that invalidates it** is not touched (Task 9, the `InvalidationLink`).
8. **A handler whose callback executor is not the Runtime's owner** is reported at construction, by affinity: a
   distinct serial executor running on the owner's thread is accepted, a pool or another thread is not (Task 10).
9. **A fetcher or runner that throws before returning a `Completion`** is the node's `error()`, not an Effect
   defect (Tasks 8, 9).
