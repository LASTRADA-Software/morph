# Declarative UI, part 6 — `morph::qt_quick` implementation plan

**Issue:** #891 (part 6 of #885). **Spec:** spec 3, `docs/superpowers/specs/2026-10-04-qtquick-frontend-design.md`,
read against what `master` holds: the UI document and its interpreter (spec 5, `include/morph/ui/document.hpp`,
`interpreter.hpp`), the view tree and its mount (`view.hpp`, `mount.hpp`, `backend.hpp`) and the frontend seam
(`frontend.hpp`).

## What planning found

Spec 3 §2–§5 describe a renderer that does not use `Mounted`: the interpreter numbers every bound property, a
generator writes one QML document per screen scope and per row template referring to those numbers (`v.s17`), and
the renderer binds that text to a value object. The code on `master` cannot feed that pipeline, and the part cannot
change it without editing the interpreter:

1. **The interpreter mounts only through `Mounted`.** `Interpreter::mount(doc, params, IViewBackend&, …)` lowers the
   document and hands the tree to `Mounted` in the same call. There is no entry point that returns the lowered tree
   without mounting it, and the queries, relations, controlled-input re-assertion and content scopes it builds are
   all expressed as `Mounted` content (a dialog's content is a one-row `forEach`; a boundary is a `Switch`).
2. **Slot ids are per instance, not per template.** `ScreenCore::nextSlot()` is a counter that every lowering of
   every row view advances, so two rows of one `forEach` have different slot ids, and a row template has no stable
   numbering a generated delegate could refer to.
3. **Row views, switch cases and dialog content are C++ closures** built per instance from a row signal; a static
   QML document for the screen cannot contain them.

So the Qt Quick renderer of this part is an **`IViewBackend`** — the same seam the terminal renderer (#919)
implements — whose widgets are Qt Quick items made from one QML component per kind (the private `MorphUi` module).
`Mounted` does the binding, the keyed reconciliation, the controlled-input re-assertion and the content scopes, so
both renderers are held to one contract and one conformance suite (`ui::testing::conformanceCases()`), on the real
Qt Quick engine here. Spec 3 is rewritten to say so (§2–§5, §11), `docs/spec/ui/view_tree.md`'s sentence about a
code-generating Qt renderer is corrected, and #891 says why.

What is kept from spec 3: every node kind maps to one `MorphUi` component; keys cross into QML as text
(`i:<int64>` / `s:<text>`) and never as a number; every QML file the renderer compiles passes `qmllint`; controlled
widgets snap back; restyling and custom components load with verification and fall back; the frontend's lifecycle.

What would change this: an interpreter entry point that lowers without mounting and numbers slots per template.
With it, a per-template generator could replace the per-widget components; `Frontend`, `Components` and the
scheduler would stay as they are, and only `Backend` would change.

## Split

The part lands as two pull requests.

- **(a) this PR — the renderer and the frontend, native.** `morph::qt_quick` (`MORPH_BUILD_QT_QUICK`), the `MorphUi`
  module, `qt_quick::Backend`, `qt_quick::Frontend` / `frontendOption`, the QTimer `Scheduler`, components and
  restyling, the spec 3 §11 offscreen suites, `qmllint` over every QML file, the CI leg that builds and runs them,
  install/export, docs. `Part of #891`.
- **(b) the WebAssembly build.** The Emscripten build of `morph_qt_quick`, the smoke executable that imports the QML
  modules generated items need (`qt_import_qml_plugins`), its CI job, the frontend's heap-held state across Qt's
  non-returning WebAssembly event loop, the browser-history route (§10) and the `getOpenFileContent` file picker.
  `Closes #891`.

Why split: (b) needs a Qt-for-WebAssembly toolchain job that only CI has (this machine has no Emscripten Qt, and the
lane is told not to try a local WASM build), its failures are link-level and unrelated to the renderer's behaviour,
and (a) is already the size of the terminal renderer. Landing (a) first lets (b) be reviewed as build plumbing
against a renderer that is already green natively.

## Packaging (spec 3 §1)

- `option(MORPH_BUILD_QT_QUICK …)`, default OFF; it requires `MORPH_BUILD_QT` (for `QtExecutor`) and Qt 6.5+
  `Quick`, `QuickControls2`, `QuickLayouts` and `Qml`; configure fails naming both when either is missing.
- `morph_qt_quick`, alias `morph::qt_quick`: a compiled STATIC library, created before the public-header guard
  (`include/morph/qt_quick/:morph_qt_quick` in its component map), linking `morph`, `morph_qt` and the Qt modules
  PUBLIC; `apply_warnings`, sanitizers and coverage as `morph_tui` has them.
- `MorphUi`: a static QML module (no plugin, no C++ types) holding the components, in its own target so morph's
  warning set does not reach Qt's generated sources; linked PRIVATE into `morph_qt_quick` and loaded by URL from
  `qrc:/qt/qml/MorphUi/`.
- Public headers, declaration-only (the code is in `src/qt_quick/`): `backend.hpp` (`Backend`, `BackendOptions`),
  `frontend.hpp` (`Frontend`, `FrontendConfig`, `ShellFactory`, `frontendOption`), `components.hpp` (`Components`,
  `ComponentFailure`) and `scheduler.hpp` (`QtScheduler`).
- Install and export as component `qt_quick`; `find_dependency(Qt6 6.5 COMPONENTS Quick QuickControls2 Qml)` in
  `morphConfig.cmake.in`; the version file is not `ARCH_INDEPENDENT` with it installed.
- Coverage: `include/morph/qt_quick` holds no executable code, so it produces no branch records and takes no
  `FLOORS` entry; its code is in `src/qt_quick`, which the `include/morph` gate does not score.

## Design

- **Context.** `Backend(QQmlEngine&, QQuickItem& host, BackendOptions)` compiles each kind's component once, on first
  use, and appends every backend root to a column it adds to `host`.
- **Widgets.** One C++ class per kind over a shared base that owns the item. Every component's root is `MorphWidget`
  (`visible`, `enabled`, layout hints in font units, tooltip, accessible name and role, surface, drag key, drop
  target, chords, column span); fields add `MorphField` (`readOnly`, `required`, `errors`, `stale`). A setter writes
  a property, and does nothing when the item already shows the value. QML reports user actions through one relay
  object per widget (`host.fire(event, payload)`); the relay calls a copy of the handler, and a destroyed widget's
  relay is dead, so no handler runs after its widget's destructor.
- **Containers** keep their children's order in C++ and apply `moveChild` as one stacking-order change; layouts
  follow stacking order. A split view uses its container API instead.
- **Keys** cross as text: a drag key, a table row's key and an option's identity never become a JavaScript number.
- **Tables** position cells by column, so a hidden cell keeps its column; a click selects, Ctrl-click extends in
  `Multiple` mode, a double click activates without toggling.
- **Overlays.** A dialog is a modal `Popup`, a drawer a `Drawer`; a dismissal by Escape or a click outside reports
  `onDismiss`, a close by `setOpen(false)` reports nothing.
- **Components** (`qt_quick::Components`): host components (registered by name and version), bundle components
  (QML text with its SHA-256), and the restyle map (kind → component). A restyle component must declare the base
  kind's properties and signals, checked on load; a bundle component must match its hash and compile in a dedicated
  engine. A failure is reported once and the caller renders the fallback.
- **Frontend.** `Frontend(int& argc, char** argv, FrontendConfig)`: `run` constructs `QGuiApplication`, a
  `QtExecutor`, the runtime, a `QtScheduler`, the engine, the window and the backend, in that order, and runs the
  source through `ui::runApp`; teardown is the reverse. `quit(code)` before the loop still ends the run. Named
  `"qt"`; usable on macOS, Windows, WebAssembly, and elsewhere with `DISPLAY` or `WAYLAND_DISPLAY` set.

## Tasks

1. This plan.
2. Packaging: the option, the targets, the `MorphUi` module skeleton, install/export, the header guard, and an empty
   test target.
3. The backend's base, the leaf kinds and the containers, with their unit tests.
4. Overlays, tabs, tables, splitters, collapsibles, drop zones and drag-and-drop, with their unit tests.
5. The conformance suite on the Qt backend (a probe driving the real engine), and the cases the probe cannot reach.
6. Lists through the interpreter (minimal moves, int64 keys above 2^53, focus across a reorder), the behaviour
   cases (a bound property follows its slot, one frame per flush, a refused selection snaps back, typing keeps the
   cursor, dismiss and reopen) and spec 5 §7's server-calculated values, observed through the rendered items.
7. Components and restyling.
8. The scheduler and the frontend.
9. `qmllint` over every QML file the renderer compiles, as a ctest case.
10. CI: build and run the suite in the all-features leg with a "the qt_quick suite ran" step; clang-tidy reads
    `src/qt_quick`.
11. Docs: `docs/spec/qt_quick/backend.md` and `frontend.md`, spec 3 rewritten where it is wrong, `view_tree.md`,
    the spec index, ARCHITECTURE and CHANGELOG.
