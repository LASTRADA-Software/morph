Detailed Description

The server side of the UI service (spec 5 §12, §12b, §13): UiRegistry collects an application's screens and files and builds a ServedBundle; UiService answers ui-hello, ui-catalog and ui-fetch from it as a RemoteServer envelope service.

◆ FieldTextSource

using morph::ui::FieldTextSource = std::function<FieldTexts(std::string_view bcp47Locale)>

Where a server reads the application's texts for a locale: a field's label, help and placeholder under the keys forms::i18n derives (<actionTypeId>.<field>.label, .help, .placeholder, or the field's x-i18nKey stem with the same suffixes), and any other message key the application translates.

Given the BCP 47 tag the request's session names, already checked by isLocaleTag; it answers the texts it has for that locale, empty for none. The host owns the storage and the language fallback (de-AT falling back to de is the source's choice to make). It is called on server threads, the server strand and the chat's worker, so it must be safe to call concurrently. One that throws is answered as a refusal.

◆ isUiServiceRead()

bool morph::ui::isUiServiceRead ( std::string_view modelType,
std::string_view actionType )
nodiscardconstexprnoexcept

Whether an authoriser is asked about one of the UI service's reads: ui's hello, catalog, fetch or texts.

An application that serves a login screen admits these for a session with no principal yet, so a client can greet the service, read the catalog, fetch the login screen and show its fields' texts in the person's language. Admitting them discloses no other screen: ui-catalog lists, and ui-fetch serves, a non-public screen only to a principal who may run its queries, which the authoriser still decides. ui-texts answers the application's words, as a bundled message catalogue holds them, and no data.

Parameters
modelTypeThe model type asked about.
actionTypeThe action asked about.
Returns
Whether it is one of those reads.
