Detailed Description

Qt WebSocket server that bridges incoming connections to a RemoteServer.

Listens for WebSocket clients, receives their text messages, and forwards each one to RemoteServer::handle(). Replies are sent back to the originating client.

TLS
Pass a QSslConfiguration to enable wss://. The configuration should be built from a certificate file, a Qt resource, or a byte array before being passed in.
Resource limits
Pass a QtWebSocketServerConfig to bound connection count, per-frame size, per-connection message rate, and handshake/idle time. All fields default to unbounded (except maxMessageBytes, which defaults to the wire-layer cap), reproducing today's behavior when omitted.
Bind address & plaintext-exposure guard
listen() refuses — returns false and logs at morph::log::LogLevel::error — when cfg.bindAddress is not loopback, no TLS configuration was passed to the constructor, and cfg.allowPlaintextExposure is false. See QtWebSocketServerConfig and security.md's "Transport security" section.
Usage
Call listen() to start accepting connections, and port() to discover the bound port (useful when port was 0 — let the OS assign a free port). Call close() or destroy the object to stop the server.

◆ closeGracefully()

bool morph::qt::QtWebSocketServer::closeGracefully ( std::chrono::milliseconds deadline)

Gracefully stops the server: refuse new work, let in-flight replies deliver, close each client with a proper WebSocket close frame, then hard-stop anything still connected.

Sequence: QWebSocketServer::pauseAccepting() (no new connections), RemoteServer::beginShutdown() (new register/execute now fail fast with "server shutting down"), waiting up to deadline for RemoteServer::drainedWithin() to report every in-flight execute has replied, sending each still-connected client a real close frame (CloseCodeGoingAway, reason "server shutting down") instead of an abort, and finally running the existing close() hard stop for whatever deadline did not leave time to finish gracefully.

Pumps the Qt event loop internally while it waits, so it is safe to call from the Qt thread — which is also the thread that must run sendTextMessage for replies and close frames to actually reach clients. Purely additive and opt-in: a server that never calls this behaves exactly as it does today, and close() itself is unchanged.

Parameters
deadlineTotal time budget for the whole sequence, measured from the moment this call starts. Whatever the drain and graceful-close steps have not finished within it is hard-stopped exactly as close() does.
Returns
true if every in-flight execute drained before deadline elapsed; false if the hard stop had to reclaim stragglers.
